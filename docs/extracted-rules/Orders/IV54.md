## 1. Purpose — what this program does

This program deletes an open purchase order that has not been received at all. For each product on the PO, it removes the PO from the product's on-order tracking in IVMST, deletes the special orders linked to the PO, and deletes the IVPO record. It also has a cleanup mode: when the PO number is not on file, the operator can enter one product and strip that PO number from the product's on-order list. It does NOT cancel partially received POs (that is `IV56`, cancel backorders), notify the vendor, or keep a cancelled-PO record.

**Important:** this program still uses the pre-PRO (PHOTO2K) IVMST positions 28/29/30 for PO tracking. In the PRO dictionary those are LAST.COST/UPC/CAT.NO, and PO tracking is at 20–23 (as used by `IV56` and `IV.ORD.REC`). See Bug suspects.

## 7. Bug suspects

- **IVMST layout clash (lines 16–18, 99–103):** under the PRO layout, `LOCATE(ORDER, MREC(28))` searches LAST.COST. Normally nothing matches, so the PO is **never removed** from the real on-order fields (20–23), leaving phantom on-order quantity. If a product's last cost happens to equal the PO number as a string (both numeric), lines 100–102 delete LAST.COST, **UPC and CAT.NO**.
- **Dictionary conflict on PO attr 14 (lines 107–110):** if attr 14 holds an FG.PCT value (per the dictionary), the program deletes an unrelated IVSPORD record whose key equals that value. PO attr 18 (stock-product special orders, per IV46.PROD) is not deleted at all, leaving orphans.
- **Duplicate check (lines 59–62 and 79–82):** the "already received" test runs twice; the second copy is dead.
- **Orphan mode (lines 46–58):** with `MAT PO=''`, the "Are you sure you want to delete PO#" prompt and "has been deleted" message refer to a PO that never existed.
- **Abort leaves locks (line 96):** `STOP` after a failed 555 read leaves IVPO and IVMST locks to be cleared at logoff.
- **No transactional guard:** IVMST updates, IVSPORD deletes and the IVPO delete are separate writes.
- READU silent-fallthrough: not present (ELSE branches are not-found; no LOCKED clause, so reads wait).

## 8. Schema-design notes for the CTO

- Modifies **PurchaseOrder** (delete), **Product.onOrder** tracking, **SpecialOrder** (delete).
- In the new system, on-order quantity should be derived from open PO lines rather than a denormalized MV list on the product. That would remove this whole class of sync bugs (and the orphan-cleanup mode).
- PO cancellation should be a status with reason, user and date, not a delete.
- Special-order disposition on PO cancel needs a business rule.
- **Variant status:** IV54 still runs on the PHOTO2K IVMST layout. Before classification, confirm whether it is on a live menu. If not, the whole program is a candidate for OBSOLETE (with IV.ORD.REC and IV56 as the PRO-era references).
