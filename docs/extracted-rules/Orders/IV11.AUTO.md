## 1. Purpose — what this program does

After goods are received, this program decides which open member orders (backorders) can now ship. It finds products with stock on hand that appear on open order lines, walks member orders oldest-first, and releases each order line in full while stock remains. It prints a warehouse pick/ship ticket per member order with a new shipping number and barcode, and marks the order "backorder printed". It runs automatically from receiving (`IV.ORD.REC` when CONTROL `ABO` = 1) or from the menu. It does NOT move stock, bill the member, or change order quantities. Stock is decremented later at scan/billing, and the allocation here exists only in memory for the run.

## 7. Bug suspects

- **Debug pauses in production (92, 111, 117):** `INPUT` waits for Enter with cryptic output. Chained from receiving, the operator sees "@SRC = n" and a bare number.
- **Rollover window defeats the cutoff (115, 160):** while the order counter is between 94000 and 99999, `@ID GT 93999` includes every order above the cutoff too, so orders newer than tickets in progress are released.
- **Priority inverted after rollover (161):** `BY ORDER` sorts 10000… (new, post-wrap) before 94000… (old, pre-wrap), so newer orders get stock first.
- **Over-allocation (187–189):** a line is released in full when any stock remains. With 3 on hand and orders for 5 and 2, the first gets 5 and the second nothing.
- **Stock reserved for a credit-hold member is lost (229):** the hold is checked again at print time, after allocation. The units allocated to that member are not reallocated to the next order in this run.
- **Stale tickets reprinted (195–196, 205):** BKORD is cleared only when the first new record is written. If nothing is allocated, last run's BKORD records are printed again, get new shipping numbers, and their orders' status is set to 1 again.
- **SKIP blank or 0 (57–58, 177):** if CONTROL `SKIP` exists with an empty attr 1, `V(7)[1,1]=''` matches every order without special instructions and they are all skipped. With SKIP = 0, any instructions starting with "0" are skipped.
- **Ticket line dropped (291–297):** after `FOR I=X2 TO X3`, I = X3+1, but the continuation test reads `BK(2)<1,I+1>`. A ticket with exactly 28 (or 55, …) lines never prints the last line.
- **Lines truncated on a missing product (282, 292):** if a released product's IVMST record is missing, `GOTO 100/130` stops printing the rest of the ticket, but the order is still marked printed.
- **Array overflow (37, 155):** more than 1000 candidate products overflows `B()`/`C()` (run-time error).
- **Run stops mid-print (223–228):** a member missing from ARMST stops the run after some tickets are printed and numbered; BKORD is left partly processed.
- **Allocation is not persisted:** the released quantities exist only in memory and on paper. If the run stops, nothing records which stock was promised.
- **READU/MATREADU silent-fallthrough (222):** `MATREADU V ... ELSE RELEASE` has no LOCKED clause, so it waits (no fallthrough on locked); ELSE is not-found only. Not present.

## 8. Schema-design notes for the CTO

- Entities: Backorder Release Run, Allocation (order line → qty released, run, date), Pick/Ship Ticket (shipping number, order, type B), Order status transitions, Exception (BKEXP).
- PIV2 should persist allocations (and reserve stock) instead of computing them in memory. That fixes the credit-hold and stale-BKORD issues and enables event-driven release per receipt (see IV.ORD.REC.36).
- Priority must be explicit: order date/time or order number without wrap, with any member-tier or dated-order rules stated as data.
- Overloaded data: dated-order code inside special-instruction text (VNORD 7); VNORD key = vendor prefix + order number; status codes `''`/0/1/2. Normalise into order type, order date, status enum.
- "Available" here (on hand only) differs from IV21 (on hand + on order − REQ) and the IVMST dictionary (`INSTK`). PIV2 needs one availability service.
- Ticket printing is warehouse execution. Keep in Computyme/WMS or move to the 3PL, while the release decision moves to PIV2.
- Missing audit: what was released to whom per run, who overrode skip settings.
- Extract before schema commit: `IV11.DHPRT` (sibling print program), `IV11` (manual backorders, if it exists), the billing/scan programs that consume VNORD status and NUMBER (`IV.UPD.SCANORD`), and `CHANGE.VNORD` (done).
