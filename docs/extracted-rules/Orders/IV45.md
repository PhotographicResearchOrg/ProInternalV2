## 1. Purpose — what this program does

This program displays or prints vendor purchase orders (IVPO) as the document sent to the vendor. It builds the vendor block (from APMST, falling back to VNMST, or from the PO itself for one-time vendor 9999), PRO's Bill-To block (with PRO's dealer number at that vendor), the terms line, special instructions, product lines with catalog number, quantity, unit and extended cost, and totals. The Ship-To is hard-coded to the Hatboro warehouse. Print mode can queue several POs in one run. It does NOT change the PO, mark it as sent, fax or email it, or convert yen to dollars.

## 7. Bug suspects

- **VNMST fallback prints garbage (lines 94–96, 145–168):** VNMST has a different layout from APMST. For a PO whose vendor exists only in VNMST (e.g. POs built by IV.ORD.REC, which store IVMST attr 5 = PRO vendor), the address lines are shifted (STREET printed as NAME2, and so on). Blank PO terms then print as `"<SURCHARGES>% <PREV.YR> OF THE MONTH"`.
- **Number collision:** APMST is read first. If a PRO vendor number (VNMST key) also exists as an AP vendor number, the PO prints a **different company's** name and address.
- **Reprint cost drift (line 208):** costs come from the current IVMST PO.COST, not from the PO, so a reprint can disagree with the original PO, with IVPO's stored cost, and with the receiving cost.
- **Mixed-currency total (lines 210, 214, 227):** yen and USD extended costs are summed into one TOTCST, then printed raw with `Y`.
- **Fax field mismatch (line 157):** APMST attr 33 is `WH.REC` in the dictionary.
- **Dead option (lines 33–35):** EOP.CLAUSE is read but never printed.
- **IVEMP attribute (line 233):** reads attr 5 for the employee name. The decoded `D_IVEMP` shows NAME at attr 4. Confirm.
- **Uninitialized `PG` in display mode:** PG is set only in print-mode queue handling (line 52). It is used only in print headings, so this is low impact.

## 8. Schema-design notes for the CTO

- Reads **PurchaseOrder**, **PurchaseOrderLine**, **Vendor** (both masters), **Product**, and company settings.
- **IVPO attr 1 is overloaded:** it may hold an AP vendor (APMST), a PRO vendor (VNMST) or the one-time vendor 9999, and nothing records which. The new PO must reference one Vendor entity unambiguously (decide: AP/remit-to vendor vs PRO vendor group), with one-time vendors modelled explicitly.
- **Secondary / care-of vendor** (attr 1 value 2) is a second relationship. Confirm whether it is still needed.
- **PO cost source:** freeze the line cost on the PO. Do not re-derive it from product data at print time.
- **Currency:** a cost string with a `Y` suffix is an ad hoc currency marker. Add currency code and FX fields per PO (CURRENCIES file exists).
- **Terms:** free text on the PO, built from APMST PCT and DUE.DAYS free text. Structure them (discount %, discount days, net days, EOM / day-of-month).
- Vendor-side PO fields: dealer/account number at the vendor (APMST 21), PO fax/email (APMST 33? and 35–37 emails), ship-to (currently constant).
- Extract `IV46`, `IV46.PROD`, `IV46.9999`, `IV.ORD.REC`, `IV.AUTO.ORDER` and `PO.DISC` before committing the PO schema.
