## 1. Purpose — what this program does

This is the header screen for entering or changing a vendor purchase order by hand. The operator picks or generates a PO number, enters the PO date and the vendor, accepts or edits the terms (pre-filled from the vendor master), and enters up to 15 special-instruction lines. If the site requires it, the operator also enters an employee number. Line entry (products, quantities, costs, special orders) is handed to the subroutine `IV46.PROD`. The program can also list a vendor's open POs. It does NOT receive goods, cancel POs, print the PO (IV46.PROD/IV45 do that), or record which vendor master (AP or PRO) the vendor number came from.

## 7. Bug suspects

- **Typo leaves a stale vendor name (lines 129–130):** `READV PAPAME FROM VNMST ...` puts the name into a misspelled variable. `PVNAME` is in **COMMON** (`I_IV46_COMMON` line 2), so an existing PO displays the **previous PO's vendor name**. When the VNMST read fails, the ELSE re-reads the same VNMST record.
- **Inconsistent vendor precedence:** opening an existing PO (line 129) looks up **VNMST only**, while entering a vendor (line 180) looks up **APMST first**. The same PO vendor number can therefore display as two different companies.
- **Unopened IVEMP (line 296):** the `IVEMP` OPEN is commented out (lines 44–46), and `IVEMP` is `FILES(9)` in COMMON. With CUSTOM flag 19 on, the READV hits an unassigned file variable, a run-time fatal error, unless an earlier program in the same COMMON session opened it.
- **Surcharge shown as terms (line 221):** VNMST attr 8 (MD1, tenths) becomes PO terms, so "35% " means 3.5% surcharge.
- **Open-PO list may be empty (line 194):** `WITH PVEND` is not in the decoded IVPO dictionary (attr 1 is `VEND`/`VENDOR`). Confirm that `PVEND` exists in DICT IVPO.
- **Manual PO numbers don't advance the counter (lines 99–121):** the counter can lag behind. Line 89–93 compensates by skipping, but numbering gaps and order are inconsistent.
- **No silent-fallthrough:** `MATREADU PO ... ELSE` (line 111) is not-found only. With no LOCKED clause the read waits.

## 8. Schema-design notes for the CTO

- Produces and modifies the **PurchaseOrder header** (number, date, vendor, terms, instructions, employee).
- **Vendor identity is the main issue:** IVPO attr 1 accepts an AP vendor (APMST), a PRO vendor (VNMST) or 9999, and stores no type. Elsewhere: `IV.ORD.REC` writes the PRO vendor (IVMST attr 5); `IV45` prints APMST→VNMST; `IV52`/`IV54`/`IV56` look up APMST only; the IVPO `VNAME` dictionary uses APMST→VNMST. The new PO needs a single typed vendor reference, plus a derived remit-to AP vendor (via VNMST.APID) if the PO stays on the PRO vendor.
- **Terms:** stop copying free text. Model structured payment terms on the AP vendor (discount %, discount days, net days, EOM rule), and keep the surcharge % on the PRO vendor separately (it is a member billing rule, not a PO term).
- IVPO attrs 14 and 18 are used by code as special-order links while the dictionary calls them FG.PCT and CBM. Resolve before mapping the IVPO SQL copy.
- Missing audit: PO created/changed by and when (the employee # is optional).
- Extract first: `IV46.PROD` (line entry, IVMST PO.CST/RAW updates), `IV46.9999`, `IV46.SPORD`, `IV46.DSCR`, `IV.ORD.REC`, `IV.AUTO.ORDER`, `IV2` (vendor maintenance).
