## 1. Purpose — what this program does

When a PO is written to vendor `9999` (a one-time or miscellaneous vendor with no vendor-master record), `IV46` calls this routine to capture or edit that vendor's details. The details are stored only on the PO, in IVPO attr 17 (`V9999.INFO`). Which fields are captured (name, address lines, etc.) is defined entirely by the PROMPTS/SCREENS records `IV46.9999`, not by code. The first value is used by IV46 as the vendor name. The routine does NOT validate anything business-specific, create a vendor master or AP record, or write the PO itself (IV46.PROD does).

## 7. Bug suspects

- **IDATE argument mismatch (208):** passes 2 arguments to the 4-argument `IDATE(DTE,PAST,FUTURE,MSG)`. A PROMPTS field with code `IDATE` fails at run time.
- **Edits lost if the operator presses Enter at the change prompt:** `CASE SEL = ''` does nothing and loops, which is safe. But `E` on an existing PO silently discards edits with no warning.
- **Out-of-range field number ignored silently (66–71).**
- **Free-text payee:** nothing checks for duplicates or ties the name to AP, so the same one-time vendor can be typed differently on every PO.
- **READU/MATREADU silent-fallthrough:** not present.

## 8. Schema-design notes for the CTO

- Entity: One-time Vendor (payee) details on a PO. Today these are an untyped multivalue list whose meaning is in PROMPTS data.
- PIV2 option: a vendor record with type `ONE_TIME` (name, address, remit-to, tax id), referenced by the PO, so AP can pay it and reports can group it.
- Missing audit: who entered or changed the payee details.
- Before migration, read PROMPTS `IV46.9999` and profile existing IVPO attr 17 data to map the value positions.
- Sibling extractions needed: `IV46` (done), `IV45` (prints `MISC.VNAME`), AP voucher entry for 9999 POs.
