## 1. Purpose — what this program does

This program receives goods against a vendor purchase order. The operator picks a PO and a receiving store, then chooses a method: receive everything, exclude backorders, or receive selected products with or without prompting. The operator confirms quantities (and can change cost). The program assigns item (serial/unit) numbers, distributes received quantity to member special orders, updates the PO's received quantities and completion flag, updates the product master, and writes a receiving log (RECLOG). It does NOT create an AP payable, check the vendor invoice, or convert foreign currency.

**Variant warning: read before classifying.** IV52 is pre-PRO code (2000, PHOTO2K era). It (a) uses an IVMST layout that does **not** match the PRO dictionary (e.g. PO tracking at 28–30 instead of 20–23, M(4) as a type code where PRO has DESC), and (b) uses five files whose OPEN statements are commented out (IVNEW, IVINV, IVSOLD, IVPHYS, IVCUST), which is a run-time fatal error the first time any of them is touched. **`IV.ORD.REC`** (2012, "Inventory ordering and receiving USING IVPO"), already extracted under `Inventory/`, is the PRO-layout receiving program. This extraction records IV52's rules for completeness. The recommended disposition is OBSOLETE once the menu check confirms IV52 is not used.

## 7. Bug suspects

- **Unopened files (lines 38–42, 50 commented):** IVNEW, IVINV, IVSOLD, IVPHYS and IVCUST are used at lines 210, 436, 528–532, 549–563, 588–594, 615, 636–637, 650, 704–717. Line 210 runs for every product in methods 1/3/4, so the program fails at run time almost immediately. **Evidence that IV52 is not run in production.**
- **IVMST layout clash (Section 6):** if it did run, it would corrupt SUB.GRP, STATUS, MORD, MPYR, RAW.COST, PO.QTY, and potentially LAST.COST, UPC and CAT.NO, and it would never clear the real on-order fields (20–23).
- **IVPO attrs 14/18 vs dictionary FG.PCT/CBM:** confirm which is current.
- **RECLOG attr 5:** the store is written where the dictionary expects Entry-Number (IV.ORD.REC.N later prompts for Entry-No from the broker).
- **TCST uses QR (line 369):** extended cost uses the raw response `QR` instead of `QUAN`. They are equal for numeric input, but after `C` (cost change) QR = 'C'.
- **Partial commit (lines 683–684):** a missing IVSPORD record during `U` does `INPUT` then `STOP`, after IVPO and IVMST have already been written. There is no transactional guard across IVPO, IVMST, IVSPORD and RECLOG.
- **Missing IVMST skipped silently (line 666):** `MATREADU ... THEN` with no ELSE. The product is not updated and no RECLOG row is written, but IVPO already shows it received.
- **Distribution loop (lines 491–497):** when the distributed total ≠ received, it re-enters label 400 after adjusting Q, which can loop indefinitely on inconsistent data.
- **Header date stale:** "Last updated 03/07/00", but the changelog says 4-7-00.

## 8. Schema-design notes for the CTO

- Entities: **Receipt / ReceiptLine** (RECLOG), **PurchaseOrderLine** received qty/date/value, **InventoryItem** (IVINV unit records), **SpecialOrderAllocation**.
- Do **not** use IV52 as a source for the IVMST layout. Use the PRO dictionary and `IV.ORD.REC`.
- PO line receipts are stored as sub-values (dates in attr 11, values in attr 12). Normalize into a Receipt table.
- The receiving cost rule (min of PO cost and product cost) needs a business decision and should be configuration, not CUSTOM flag 14.
- Vendor: receiving has no AP link. If the Vendor Desk wants three-way match (PO / receipt / invoice), it has to be designed new.
- Before schema commit: compare with `IV.ORD.REC` / `IV.ORD.REC.N` (extracted) and extract `IV46.PROD`, `IV46.SPORD` (special orders) and the label/receiving-report programs.
